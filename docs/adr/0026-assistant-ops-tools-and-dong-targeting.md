# ADR-0026: AI 비서 운영 도구 확충과 공지 동 타게팅

- 상태: Accepted
- 날짜: 2026-08-01
- 관련: [ADR-0007](0007-readonly-tool-agent.md)(읽기 전용 도구 에이전트) · [ADR-0023](0023-parking-occupancy-persisted.md)(주차 점유 영속화) · [ADR-0024](0024-assistant-inquiry-triage.md)(민원 트리아지) · [ADR-0025](0025-agent-depth-plan-clarify-structured.md)(에이전트 심화) · [09 §8.22](../09-implementation-harness.md)(H19 체크리스트)

## 맥락

시나리오 자료 2종이 들어왔다(2026-08-01).

- **(A)** `260725공지사항정리_질문시나리오추가완료.xlsm` "질문시나리오" 탭 6건(Q08-01~06) + 구두 추가 5건
  (관리비 세대평균 비교 · 커뮤니티 놀이터 이용시간/사용료 · 주민공동시설 이용시간 · 관리비+납부규정 하이브리드 ·
  우리집 6월 관리비).
- **(B)** `LLM_질의응답_시나리오_0801_손종혁.xlsx` — 첫마을4단지 디지털트윈 LLM 질의응답 시나리오
  (관리자 3 · 입주자 3 + 공통 규칙). 원문은 별도 데모(FastAPI+SQLite+주차 시뮬)를 전제로 쓰였고,
  **LIVIQ 본체로의 이식**이 판단 대상이다.

현재 에이전트 도구는 12종(`search_documents` `search_facility_graph` `get_fees` `get_my_inquiries`
`get_facilities` `get_overdue_checks` `find_in_floor_plan` `find_nearest_available_parking`
`search_similar_inquiries` `get_recent_notices` `trace_home_device_issue` `ask_clarification`)이다.
갭을 훑으면 세 종류의 문제가 나온다.

1. **공지가 동별로 쪼개져 있는데 검색은 유사도만 본다.** 8월 공지 86건 시드
   (`apps/api/scripts/data/notices_demo.py`)에서 승강기·저수조·전기설비 점검은 401~405동 **5건씩** 본문이
   거의 동일하다. `search_documents`는 임베딩 유사도로만 뽑으므로 401동 입주민에게 403동 일정이 근거로
   붙을 수 있다. Q08-01·04("우리 동 8월 공지")의 정확도가 여기에 걸린다.
2. **관리자 운영 질의(ADM-1 외부차량 장기주차 · ADM-2 민원 현황 요약)를 받을 도구가 없다.**
   데이터는 이미 있다 — 주차 점유는 `parking_vehicles.spot_no`·`entry_at`이 실데이터(입주민 248 + 외부 8,
   H16/ADR-0023), 민원은 `get_my_inquiries`(본인)·`search_similar_inquiries`(유사 사례)만 있어 기간·동·상태
   집계 경로가 없다. 여기서 걸리는 제약은 **개인정보 노출 경계**다 — 관리자라고 해서 LLM 컨텍스트에
   민원 본문·작성자·번호판을 통째로 넣을 이유는 없다(규칙 2).
3. **"우리 집이 평균보다 많이 나왔나"를 답할 수단이 없다.** `get_fees`는 본인 세대 + 전월 대비만 본다.
   단지 평균 비교는 tenant **안**의 다른 세대 데이터를 집계하는 것이라, 규칙 3(tenant 격리)·규칙 5
   (관리비는 확정 업로드 데이터가 단일 출처, AI는 계산·부과 금지)와의 관계를 먼저 정리해야 한다.

## 결정

**세 가지를 결정한다. ①공지의 동 구분은 도구 인자가 아니라 검색 필터로 처리한다. ②관리자 운영 질의는
집계·상태만 내보내는 읽기 전용 도구 2종으로 받는다. ③단지 평균 관리비 비교는 같은 면적대 평균만,
표본 수 하한을 두고 채택한다.**

### 결정 1 — 공지 동 타게팅은 검색 필터

로그인 세대의 동을 `ToolContext`(코드가 주입하고 LLM이 절대 지정할 수 없는 격리·소유권 값 — 기존
`tenant_id`·`visibilities`와 같은 자리)에 실어, 검색 SQL의 notice 분기에서 대상 동이 다른 청크를 배제한다.
`notices.target_buildings`(JSONB · `buildings.id` **문자열** 배열 · 비어 있으면 전체동)는 이미 존재하고 검색 SQL이
`notices`를 조인하고 있으므로 **스키마 신설 없이 조건 하나**로 끝난다. 관리자·동 미상 사용자에게는
필터를 적용하지 않는다(전 동 검색 유지).

구현 시 정정 2건(H19-1 실측). ①대상 동은 애초에 **동 이름이 아니라 building id 문자열**이다
(모델 주석·작성 경로·시더 일치 — 이 문서와 09 §8.22의 "`buildings.name` 배열"이 오기였다).
②전체동 판정은 `IS NULL`로 부족하다 — 작성 경로가 파이썬 `None`을 그대로 넣고 JSONB 컬럼은 그것을
**SQL NULL이 아니라 jsonb `null`**로 저장한다(SQLAlchemy `none_as_null` 기본값). 두 형태가 섞이므로
"배열이 아닌 값은 전체동"(`jsonb_typeof <> 'array'`)으로 판정한다. 실 PG 테스트가 이 함정을 잡았다
(전체동 공지가 통째로 배제됨 — mock만 썼다면 통과했을 회귀).

캐시도 같은 값으로 갈라야 한다: tenant 스코프 답변 캐시 키(`app/answer_cache.py`)에 동 세그먼트를
넣지 않으면 401동 답변이 403동에 재생돼 SQL 필터가 무력화된다(roles·visibilities와 같은 이유).

### 결정 2 — 관리자 운영 집계 도구 2종, 노출은 집계·상태까지

- `find_longterm_parking`(MANAGER·FACILITY = 기존 `FACILITY_ROLES`) — 입주민 미등록 차량
  (`household_id IS NULL`) 중 `entry_at` 경과가 임계를 넘은 면을 경과 내림차순으로. **번호판은 내보내지
  않는다**(면 번호와 경과시간이면 현장 확인에 충분하다).
- `summarize_inquiries`(MANAGER·STAFF) — 기간·동·상태별 집계 수치 + 미처리 우선 목록(제목·분류·상태·경과).
  **민원 본문·작성자는 SELECT 자체를 하지 않는다**(H17-1 `search_similar_inquiries`가 `is_mine` 불리언만
  내보내고 테스트가 SQL 문자열까지 단언한 선례를 따른다).

역할 가드는 서버에서 이중으로 건다(규칙 4) — 역할 밖 사용자에게는 도구 **스펙 자체를 노출하지 않고**
(`allowed_roles`), 실행 경로에서도 거부한다. 두 도구 모두 읽기 전용이다(규칙 8 · ADR-0007).

### 결정 3 — 단지 평균 관리비 비교: 채택(같은 면적대 · 표본 하한)

**채택한다.** 조건 셋을 함께 건다.

- **같은 단지·같은 면적대 평균만** 제시한다(면적이 다른 세대와의 비교는 정보가 아니라 오해다).
- **개별 세대 금액은 어떤 경로로도 노출하지 않는다** — 반환 스키마에 필드를 두지 않는다.
- **표본 수 하한 k 미달이면 비교를 거부하고 본인 세대 값만 답한다.** 소표본 평균은 특정 세대 금액을
  역산시킨다(극단적으로 n=2면 평균과 내 값에서 상대 세대 값이 그대로 나온다). k의 구체 값은 착수 시
  실제 면적대 분포를 보고 정한다.

규칙 3은 tenant **간** 격리이지 tenant **내** 집계 금지가 아니다 — 같은 단지 안의 집계는 격리 위반이
아니고, 위험은 격리가 아니라 **소표본 역산**이므로 하한 k가 그 위험을 직접 막는 통제다. 규칙 5와도
저촉하지 않는다: 평균 비교는 **확정 업로드 데이터를 조회한 집계값을 제시**하는 것이지 AI가 관리비를
계산·부과하는 것이 아니다(화면 숫자는 도구 확정값 그대로 — ADR-0025의 `ToolCard.data` 원칙과 동일).

(작성 시점의 문서 상태는 `Proposed`였고, 결정 3만 사용자 승인이 끝난 채택이었다. 이후 결정 1·2·3이
H19-1·H19-3·H19-4로 전부 구현되어 상태를 `Accepted`로 올렸다 — [09 §8.22](../09-implementation-harness.md).)

## 대안

**결정 1 — 공지 동 타게팅**

| 안 | 내용 | 판정 |
|---|------|------|
| ① 검색 필터(채택) | `ToolContext`의 동으로 검색 SQL에서 배제/감점 | **채택** — 스키마 신설 0, LLM 라우팅 예산 0, 모델이 틀릴 여지 자체가 없다(격리 값을 코드가 주입) |
| ② 본문에 동 강조 | 인제스트 시 청크 텍스트 앞에 "401동" 등을 덧붙여 임베딩이 구분하게 | 기각 — 유사도는 확률이라 **보장이 아니다**. 완료 기준 "타 동 공지 인용 0건"을 만족시킬 수 없고, 재색인 비용도 든다 |
| ③ 도구 인자로 동 받기 | `search_documents(dong=...)`처럼 LLM이 인자를 채움 | 기각 — 8B는 **인자가 늘수록 라우팅·인자 생성이 함께 무너진다**(R22 계열 실패, `tools/notices.py` 주석이 같은 이유로 `get_recent_notices`를 무인자로 확정). 게다가 동은 사용자가 말하는 값이 아니라 **로그인 세션이 아는 값**이라, LLM에게 물을 이유가 없다 |

**결정 2 — 관리자 도구**

- *기존 도구에 역할별 분기 추가*(예: `get_my_inquiries`가 관리자면 전체 집계) — 기각. 한 도구가 역할에
  따라 다른 것을 반환하면 도구 설명이 모호해져 8B 라우팅이 흔들리고(H17-1 실측: 설명 경계가 무너지면
  도구 선택이 정확히 반대로 갈렸다), 인가 실수도 한 함수에 몰린다.
- *민원 본문까지 반환*(요약 품질 향상) — 기각. 관리자는 민원 화면에서 본문을 볼 수 있다. LLM
  컨텍스트로 본문·작성자를 밀어 넣는 것은 규칙 2의 노출면을 이유 없이 넓힌다.

**결정 3 — 평균 비교**

- *금지(폴백 유지)* — 기각. 사용자 승인으로 채택됐고, 소표본 역산 위험은 하한 k로 직접 막힌다.
- *분위(백분위)까지 노출* — 보류. 평균보다 정보량이 많지만 소표본에서 역산 위험도 함께 커진다.
  평균만으로 시나리오가 충족되므로 지금은 넣지 않는다(YAGNI).

**범위 밖 — 입주민 3D 화면 연동**

B문서 공통 규칙의 "화면 연동(3D 카메라 이동·비콘)"은 관리자 화면에 이미 있다(H14 시설 그래프·주차장 3D).
입주민 앱은 H17-2의 **2D 주차맵 + `?spot=` 딥링크**로 충족시키고, **입주민 3D는 범위 밖(백로그)**으로 둔다 —
입주민 화면은 폭 ~430px에서 쓰이고, 자기 차 한 대의 위치를 찾는 데 3D 카메라 이동이 주는 이득이 없다.

## 결과

- **이득**: 동별로 쪼개진 공지가 정확해진다(Q08-01·04). 관리자 운영 질의 2종(ADM-1·ADM-2)과 입주민
  RES-1(내 차 위치)이 화면이 아니라 대화로 열린다. 관리비 평균 비교는 가장 자주 나오는 질문
  ("우리 집이 많이 나왔나")에 확정 데이터로 답한다.
- **비용**: 도구가 12 → 15종이 된다. 8B는 도구 수가 늘수록 라우팅이 흔들리므로(R22·R28 관측),
  H19-3·H19-5의 완료 기준에 **라우팅 회귀 없음**을 명시했다. 회귀가 나면 도구 설명 경계를 재작성한다
  (H17-1 관례 — 실측으로 되돌린 기록이 ADR-0024 §실측).
- **후속**: 케이스셋 v2.1 + dev 3회 재측정(H19-5). 인용률 비교는 **3회 이상 중위로만** 판정한다
  (H18 R30·R30b에서 단발 회차 비교가 분산을 증감으로 오독하게 만든 전례).
- **되돌릴 신호**:
  - 도구 3종 추가 후 골든셋 라우팅률이 R30 범위를 벗어나면 → 도구 통합 또는 역할별 스펙 축소를 재검토.
  - 동 필터가 전체동 공지(`target_buildings` NULL) 회수를 떨어뜨리면 → 배제 대신 감점으로 완화.
  - 실제 면적대 분포에서 하한 k를 만족하는 세대가 소수라면 → 평균 비교를 면적대 대신 단지 전체로
    올리거나(정보 가치 하락) 기능을 접는다.
