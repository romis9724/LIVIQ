# ADR-0025 — 에이전트 심화: 계획 turn · 멀티턴 · 되묻기 · 구조화 응답

- 상태: Accepted (H18)
- 날짜: 2026-08-01
- 관련: [0007](0007-readonly-tool-agent.md)(읽기 전용 도구 에이전트 — 이 ADR이 확장) · [0024](0024-assistant-inquiry-triage.md)(민원 트리아지) · [01 §5.2·§6](../01-architecture.md) · [09 §8.21](../09-implementation-harness.md)

## 맥락

사용자 평가(2026-08-01): **"답이 단조롭다. 이건 에이전트가 아니라 단순 챗봇 같다."** 코드를 보면 진단이 맞다.

1. **대화 컨텍스트가 LLM에 전달되지 않는다.** `answer_question(question: str)`은 질문 한 개만 받는다.
   `conversation_id`는 DB 저장용일 뿐이라 "그럼 언제까지야?" 같은 후속 질문이 원리적으로 불가능하다.
2. **되묻지 않는다.** 모호한 질문에도 바로 답하거나 근거 부족으로 폴백한다. 명확화 경로가 없다.
3. **계획이 없다.** 도구 루프 3스텝이 전부다. 무엇을 왜 조회할지 정하는 단계, 중간 결과를 보고
   전략을 바꾸는 단계가 없다.
4. **출력이 평문 한 덩어리다.** 관리비 항목·주차 자리·시설 상태가 전부 도구 카드 안에서 구조를
   잃고 문장으로 녹는다. 화면에는 문단과 인용 카드뿐이다.
5. **직전 "2~4문장" 지시의 영향은 측정 범위 내였다.** dev 2회 재측정에서 인용 83.5·86.1%로
   R29 기준선(86.1·88.6·87.3%)보다 중위가 낮았지만 **범위가 겹쳐 인과를 단정할 수 없다**
   (pass 62·65, 도구 선택 89.9%는 기준선과 동일). H15-2 R21에서 답변을 짧게 만드는 압력이
   인용을 함께 지운 선례가 있어 방향은 의심스럽지만, 이 데이터로는 확정되지 않는다.
   길이 지시를 되돌리는 이유는 인용률이 아니라 **단조로움의 원인이 길이가 아니라 형식과
   상호작용이기 때문**이다 — 짧게 쓰라는 지시는 형식을 풍성하게 만드는 방향과 상충한다.

인터뷰 확정(2026-08-01): 실행 구조는 **직접 구현 유지 + 계획 단계 추가**, 멀티턴 컨텍스트와
명확화 되묻기 **둘 다**, 응답은 **구조화 블록 · 다음 행동 제안 · 도구 과정 노출 · 길이 완화**,
UI 레퍼런스는 **Perplexity 계열**(출처 우선·단계 표시·맥락 기반 후속 질문).

## 결정

### 1. LangChain/LangGraph를 도입하지 않는다

ADR-0007의 직접 구현을 유지한다. 마스킹 fail-closed(규칙 2)·스텝 상한·테넌트 주입(규칙 3·4)·
인용검증(규칙 1)이 전부 `orchestrator.py` 한 파일의 직선 흐름 안에 있고, 그래서 게이트가
"빠뜨릴 수 없는" 구조다. LangGraph로 옮기면 같은 게이트를 노드 경계마다 다시 심어야 하고,
빠뜨려도 테스트가 아니면 드러나지 않는다. 지금 필요한 것(계획 1스텝·히스토리 N턴·되묻기 1종)은
전부 기존 루프에 얹을 수 있다.

재검토 조건: 병렬 도구 실행·체크포인트 재개·휴먼인더루프 승인 흐름이 실제 요구가 될 때.

### 2. 계획은 별도 turn이 아니라 **루프 안의 무-도구 turn**으로 표현한다

현재 루프는 `tool_calls`가 없으면 즉시 break한다. 이를 바꿔, **content만 있고 도구 호출이 없는
turn은 "계획"으로 간주해 대화에 남기고 1회 한정으로 계속 돈다.** 별도 LLM 호출을 추가하지
않으므로 지연·비용 증가는 계획을 실제로 세운 질의에만 생긴다.

- 스텝 상한 `MAX_TOOL_STEPS` 3 → **4**(계획 1 + 도구 3).
- 계획 turn은 최대 1회. 두 번째 무-도구 turn은 지금처럼 종료 신호로 본다(무한 루프 방지).
- `AGENT_SYSTEM_PROMPT`에 "복합 질문이면 무엇을 조회할지 한 줄로 정한 뒤 도구를 부르라"를 넣는다.

### 3. 멀티턴 컨텍스트 — 직전 N턴만

`answer_question(question, history=...)`로 직전 **3턴**(user/assistant 쌍)의 텍스트를 도구 결정
turn과 최종 답변 turn에 함께 넣는다.

- 히스토리는 **답변 본문만**(도구 카드·인용 원문은 재전송하지 않는다 — 토큰 폭증 방지).
- 각 턴은 상한 400자로 자른다.
- **히스토리가 있으면 답변 캐시를 우회한다.** 같은 질문도 맥락에 따라 답이 달라지므로 캐시 키에
  히스토리를 넣으면 적중률이 0에 수렴한다 — 차라리 첫 턴만 캐시한다.
- 히스토리도 `ensure_masked`를 통과한다(규칙 2 — 예외 없음).

### 4. 되묻기는 **특수 도구** `ask_clarification`으로 표현한다

새 이벤트 종류나 별도 분류 turn을 만들지 않는다. LLM이 모호하다고 판단하면 다른 도구와 똑같이
`ask_clarification(question=...)`을 고르고, 오케스트레이터가 이를 만나면 도구를 실행하는 대신
**즉시 `DoneEvent(status="clarify")`로 되묻고 종료**한다.

- 라우팅 메커니즘·역할 필터·인자 검증이 전부 재사용된다. 새 코드 경로가 거의 없다.
- 남발 방지: 도구 설명에 "정보가 여러 개로 갈려 답을 특정할 수 없을 때만"을 명시하고,
  **직전 턴이 clarify였으면 이 도구를 스펙에서 제외한다**(연속 되묻기 금지).
- 되묻기는 근거 없는 답변이 아니므로 규칙 1에 저촉되지 않는다. 인용도 요구하지 않는다.

### 5. SSE는 4종을 유지하고 **필드만 additive 확장**한다

이벤트 종류 추가는 하지 않는다(docs/09 §1.1 계약). 대신:

| 이벤트 | 확장 | 하위호환 |
|---|---|---|
| `status` | `tool: string \| null` 추가 — 지금 실행 중인 도구 이름 | 기존 소비자는 `stage`만 읽으면 동작 |
| `done` | `status`에 `"clarify"` 리터럴 추가 | **주의: 리터럴 확장이다.** 웹은 `answered`/`fallback` 외를 폴백으로 취급하고 있어 안전하지만, 계약 문서와 타입을 함께 고친다 |
| `citation` | `data: object \| null` 추가 — 도구 결과의 구조화 페이로드(표·목록) | 없으면 기존처럼 텍스트만 렌더 |
| `done` | `suggestions: string[]` 추가 — 다음 행동 제안 | 빈 배열이면 렌더 안 함 |

`stage` 리터럴 3종(searching·generating·verifying)은 그대로 둔다.

### 6. 구조화 응답은 **도구가 만들고 LLM은 건드리지 않는다**

`ToolCard`에 `data: dict | None`을 추가한다. 관리비는 항목 표, 주차는 자리 목록, 시설은 상태
카드가 그대로 실린다. **LLM은 이 데이터를 재작성하지 않는다** — 화면에 뿌려지는 숫자는 도구가
확정한 값 그대로여야 한다(규칙 5·8). LLM에는 지금처럼 요약 텍스트만 준다.

### 7. 다음 행동 제안은 **코드가 규칙으로 만든다**

LLM 호출을 추가하지 않는다. `tool_path`와 도구 결과를 보고 코드가 후보를 고른다
(예: `get_fees` → "지난달과 비교하기", 폴백 → "담당자 연결"). 방금 지운 고정 추천 칩과 다른 점은
**맥락 의존**이라는 것이다.

> **개정 (2026-08-01, 사용자 실측)** — 초안은 이동·행동 문구까지 담았다가 실패했다. 칩은 그
> 문구를 **새 질문으로 전송**하는 물건이라, "원문 문서 열어보기"를 누르자 사용자 말풍선으로
> 전송되고 AI가 근거를 못 찾아 폴백했다. 이후 매핑은 **질문형만** 담는다(현재 `get_fees`
> 하나). 화면 이동은 CTA 링크가, 행동은 폼이 한다. 빈 칸을 억지로 채우지 않는다 — 잘못된
> 칩은 없느니만 못하다. 이동이 유용한데 CTA가 없는 도구(`search_documents`·
> `find_in_floor_plan`·`get_my_inquiries`)는 칩으로 흉내내지 않고 후속으로 남긴다.

### 8. 답변 길이 지시를 되돌린다

"2~4문장" 지시를 걷어내고 "핵심을 먼저, 근거마다 인용, 항목이 여럿이면 목록"으로 바꾼다.
길이 상한 대신 **형식**을 지시한다. 인용률 하락은 측정 범위 내라 근거로 쓰지 않는다(§맥락 5) —
되돌리는 이유는 길이 압박이 구조화·다단계 응답과 상충하기 때문이다. 변경 후 재측정한다.

## 대안 (기각)

- **LangGraph 도입**: 위 §1. 게이트 재구축 비용과 규칙 위반 리스크가 이득보다 크다. 기각(재검토 조건 명시).
- **명확화 전용 분류 turn**: 질의마다 LLM 호출 +1. 도구로 표현하면 0. 기각.
- **계획 전용 turn(항상 실행)**: 단순 질의에도 지연·토큰이 붙는다. 무-도구 turn 재해석이면 계획이
  필요한 질의에만 비용이 든다. 기각.
- **SSE 이벤트 종류 추가(`plan`·`suggestion`)**: 소비자 전부를 고쳐야 하고 계약이 늘어난다.
  기존 4종에 필드를 얹으면 하위호환이 공짜다. 기각.
- **LLM이 구조화 JSON을 생성**: 8B가 표를 재작성하면 숫자가 틀린다(규칙 5 위반 경로). 기각.

## 결과

- 도구 1종(`ask_clarification`) 추가 — 11종. 8B 라우팅 회귀는 골든셋으로 감시한다.
- 멀티턴 케이스가 골든셋에 없다 — 2턴 이상 케이스를 신설해야 회귀를 잴 수 있다.
- 히스토리 있는 질의는 캐시를 안 타므로 원가가 오른다. 대시보드 캐시 적중률 지표 해석이 바뀐다.
- `packages/api-types` 재생성 필요(SSE 스키마 변경).
