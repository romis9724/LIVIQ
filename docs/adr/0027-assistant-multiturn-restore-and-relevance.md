# ADR-0027: 멀티턴 확장 — 서버 대화 복원과 히스토리 관련성 필터

- 상태: Accepted
- 날짜: 2026-08-01
- 관련: [ADR-0025](0025-agent-depth-plan-clarify-structured.md)(멀티턴 컨텍스트·되묻기·계획 turn) · [09 §8.22](../09-implementation-harness.md)(H19 체크리스트)

## 맥락

사용자 피드백 2건(2026-08-01).

1. **"이전 대화를 기억하고 있나요? 이어서 대화를 할 수가 없는 것 같아요."**
   멀티턴 자체는 H18에 있다 — 서버가 대화를 DB에 적재하고 직전 3턴(턴당 400자)을 재주입한다
   (ADR-0025 §3). 체감이 안 되는 이유는 **대화 보관이 탭 수명**(sessionStorage)이라는 것이다:
   새 탭·브라우저 재시작이면 빈 화면에서 시작하고, `conversation_id`도 함께 사라져 서버 히스토리에
   다시 붙을 방법이 없다. 서버에는 대화가 그대로 있는데 클라이언트가 열쇠를 버리는 구조.
2. **"관련 없는 대화는 제외하고 관련 있는 대화만."**
   현행 히스토리 주입은 관련성 무관 — 무조건 직전 3턴이다(`_prepare_history`,
   [orchestrator.py](../../packages/ai-core/src/ai_core/orchestrator.py)). 주차 얘기를 하다가
   관리비를 물으면 주차 턴이 그대로 실려 들어가 도구 결정을 오염시킬 수 있다. 특히 대화가
   영구화(결정 1)되면 한 대화가 길어지므로 이 필터가 전제 조건이 된다.

## 결정

### 1. 서버 대화 복원 (H19-8)

사용자 선택(2026-08-01): 탭 수명 유지가 아니라 **서버 복원**.

- `GET /assistant/conversations/latest` 신설 — 로그인 사용자 본인의 가장 최근 `resident` 채널
  대화 1건과 마지막 메시지들(상한 40 = 프론트 `MAX_STORED_MESSAGES`)을 반환. 대화가 없으면
  `conversation_id: null` + 빈 배열(404 아님 — 첫 방문이 오류가 아니다).
- 프론트는 마운트 시 sessionStorage 복원을 **1차**로 유지(탭 내 이동·뒤로가기의 즉시 복원,
   스트리밍 steps까지 보존), 비어 있을 때만 서버에서 복원한다(2차 폴백). 복원 실패는 조용히
  빈 대화 — 복원은 편의 기능이고 화면을 막으면 안 된다(session-store와 같은 원칙).
- **텍스트 위주 복원**: 과거 메시지는 본문·역할·상태만 되살린다. 구조화 표(`ToolCard.data`)·
  CTA·"답변 과정"(steps)은 복원하지 않는다 — 서버가 메시지에 저장하는 것이 본문·인용 행뿐이고
  (구조화 페이로드·진행 단계는 SSE 일회성), 과거 답변의 CTA를 되살릴 가치도 낮다. 복원 메시지는
  `citations: []`·`steps: []`로 채워 렌더 계약(배열 필수)을 지킨다. 본문 끝 `[n]` 마커는
  표시 계층이 이미 벗긴다(H19-6).
- **"새 대화" 버튼 신설**: 복원으로 대화가 영구화되므로 끊고 시작할 수단이 필요하다.
  메시지·`conversation_id`·sessionStorage를 비운다(서버 대화는 그대로 — 삭제 아님).
- 개인정보: 노출면은 로그인 세션과 동일하다 — 본인(user_id 소유권 검증) + tenant RLS 이중
  방어(규칙 3·4), 응답에 타 사용자·타 세대 데이터 없음. LLM 호출 없음(규칙 2 무관).

### 2. 히스토리 관련성 필터 (H19-9)

- 후보 풀을 직전 3턴 → **직전 10턴**으로 넓히고, 주입은 여전히 **최대 3턴**: 직전 1턴은 무조건
  포함(지시대명사 "그거 언제야?" 해소), 나머지 2턴은 질문과의 관련성 상위 순.
- 관련성 1차 구현은 **lexical**(문자 bigram 중첩 등 순수 함수 — LLM·임베딩 호출 없음, 지연 0,
  단위 테스트 가능). 임베딩 유사도 승격은 실측이 lexical의 한계를 보일 때만(ADR-0024 임베딩
  승격 보류와 같은 원칙 — 측정 없이 비용을 들이지 않는다).
- 판정은 골든셋 멀티턴 케이스 확충(현 3건 → 15건+, 관련·무관 턴 혼합 대화 포함) 후 3회 중위
  비교(R30b 규율). 무관 턴이 섞인 대화에서 도구 선택·인용이 오염되지 않는 것이 완료 기준.

## 대안 (기각)

- **localStorage 영구 보관**: 서버 왕복 없이 해결되지만 공유 기기에 대화(세대·차량 정보 포함)가
  로그아웃 후에도 남는다 — 세션 쿠키와 수명이 어긋나는 보관은 만들지 않는다(H17 결정 유지).
- **대화 목록 UI(스레드 브라우저)**: 최근 1건 자동 복원으로 사용자 요구("이어서 대화")는 충족된다.
  목록·검색·삭제는 수요가 확인되면(YAGNI).
- **관련성 판단을 계획 turn(LLM)에 위임**: 8B가 결정 turn에서 이미 도피 패턴을 보였고(R31),
  토큰 비용이 붙는다. 결정적·무비용인 코드 필터가 먼저다.

## 결과

- H19-8: api 라우터(`GET /assistant/conversations/latest`) + 스키마 + 프론트 복원 폴백·새 대화
  버튼 + 매핑 순수 함수. 상태·측정은 [09 §8.22](../09-implementation-harness.md).
- H19-9: `_prepare_history` 후보 풀 확장 + 관련성 선별 순수 함수 + 멀티턴 골든셋 확충 + dev 측정.
