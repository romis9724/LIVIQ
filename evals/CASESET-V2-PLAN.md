# 케이스셋 v2 설계 — 첫마을 실데이터 기반 (H15-2 후속)

> 상태: **설계안(리뷰 대기)** · 작성 2026-07-30 · 근거: [MEASUREMENT-LOG.md](results/rag500/MEASUREMENT-LOG.md) R18~R22

## 1. 왜 다시 만드는가 — v1(quality-cases-500)의 구조적 한계 3가지

| # | 한계 | 실측 근거 |
|---|---|---|
| 1 | **가상 fixture 기반** — 500건 전부 TENANT-A(해오름 합성 코퍼스). 실단지(첫마을 4단지) 등장 0회. 시드된 실데이터(문서 34·관리비 6개월·민원 32·설비 37·평면도 108)와 무관 | 케이스 CSV 전수 확인 |
| 2 | **커버리지 편중** — 문서 RAG 중심. 시설 4도구는 R22 급조 스모크 20건이 전부, `get_my_inquiries`는 정면 측정 **0건**. 라벨 결함 27건은 이미 보정(R18)했으나 같은 방식(케이스 먼저, 데이터 나중)의 산물 | R18·R22 |
| 3 | **측정 환경 혼재** — 맥북 api ↔ SSH 터널 ↔ GPU 서버 경유가 지연 수치 오염(TTFT 20ms vs 107ms). 노트북 로컬 스택 자체가 재현 불가 환경 | R14 |

v1은 폐기하지 않는다 — **"합성단지 회귀 세트"로 강등**. 채점기·하니스 회귀 검증과
케이스 형식 호환성 확인에만 쓰고, 품질 판정의 정본은 v2다.

## 2. 원칙

1. **라벨은 데이터가 정본.** 기대 사실·기대 인용·기대 도구를 전부 **DB 조회·문서 원문에서
   스크립트로 생성**한다. 모델 출력을 라벨 근거로 쓰면 순환 논리(R18에서 실패한 방식).
2. **측정은 개발서버에서만.** api·worker·DB·러너 전부 개발서버, vLLM은 사내망 직결
   (192.168.10.171:8077). 맥북은 SSH 조종석만. 지연 수치가 곧 운영 수치가 된다.
3. **케이스에 도구 기대를 명시한다.** v1에 없던 `expected_tool` 컬럼 신설 — R22가 보여준
   라우팅 실패(죽은 도구 `get_overdue_checks`)는 인용 적중률만 봐서는 영영 안 보인다.
4. **스냅샷 고정.** 라벨 생성 시점의 데이터 스냅샷(카운트·해시)을 케이스셋에 동봉한다.
   시드 재실행·데모 조작으로 데이터가 바뀌면 라벨이 조용히 썩는다(v1 R2 진부화 재발 방지).
5. **개인정보 검증 내장.** 민원·세대 케이스는 절대 규칙 2(마스킹 fail-closed) 검증을 겸한다 —
   응답에 실명·동호수 원문이 새는지 채점기가 본다.

## 4. 구성 — 300건

500 → 300으로 줄인다. v1에서 카테고리당 판별에 실제 쓰인 것은 Critical 180이었고,
3회 반복 프로토콜 비용(회당 ~40분)을 고려하면 300이 상한이다.

|---|---:|---|---|
| 관리규약 조항 | 40 | search_documents | 규약 원문(clause 단위 — R20 배선 활용) |
| 지침·매뉴얼 | 40 | search_documents | 매뉴얼 10종 원문 |

- 실행 세트: **Smoke 40**(카테고리별 최소 2) · **Critical 150** · Full 300.
- 다중 턴 20%(60건) — v1 비율 유지. 역할 배분: RESIDENT 중심 + FACILITY(시설 도구)·MANAGER 소수.
- CSV 스키마는 v1 호환 + 신설 2컬럼: `expected_tool`(콤마 허용) · `label_source`(라벨을 만든
  쿼리·문서 위치 — 감사 추적).

## 5. 채점 확장 (rag500-score.mjs)

- **도구 선택 정확도** 신설: `expected_tool` 대비 실제 호출(SSE tool_path) 일치율 — 카테고리
  집계에 포함.
- **마스킹 게이트** 신설(Hard Gate 6종째): 민원·세대 케이스 응답에 시드 실명·동호수 원문
  노출 시 즉시 fail(절대 규칙 2).
- **스텝 낭비 지표**: 같은 도구+같은 인자 반복 호출 수 기록(R22에서 26% 확인 — 개선 과제
  판정용 기준선).
- 기존 유지: 문서 단위 인용 적중 · 폴백 정확도 · 프롬프트 누출 · 3회 반복 = 범위 판정.

## 6. 이행 순서

1. **시드 변주 추가** — facilities 3건(점검 임박 2·이상 상태 1) + incidents 1~2건 보강.
   측정 전용임을 시드 스크립트에 명시(데모와 충돌 없음 확인).
2. **라벨 생성기** `evals/fixtures/chetmaeul-v2/gen_labels.py` — DB·문서 원문에서
   expected_facts·expected_citations·expected_tool 자동 생성 + 스냅샷 매니페스트 기록.
3. **케이스 작성** — 질문문은 수작업(자연스러운 입주민 언어), 라벨은 생성기 출력만 사용.
4. **모델 무관 감사** — `audit_citation_labels.mjs` 방식 재사용, 전 건 통과 후 확정.
5. **개발서버 기준선 3회** — Critical 150 × 3, 캐시 오프. 이것이 v2 정본 기준선.
6. v1은 Smoke 50만 회귀 세트로 유지(하니스 변경 검증용).

## 7. 열린 질문 (리뷰 요청 포인트)

1. 300건 규모 적정성 — 카테고리당 최소 판별력(±8%p 변동폭에서 유의미) 기준으로 더 줄일 수 있나?
2. 시설 양성 케이스를 위한 시드 변주(§6 ①)가 "측정용 데이터 조작"으로 오염 소지가 있는가?
   (대안: 이상 상태 케이스를 부정 응답 정답으로 유지)
3. 민원 마스킹 게이트의 채점 방법 — 시드 원문 사전 대조 vs 패턴(이름·동호수 정규식) 중 무엇이 덜 취약한가?
4. 다중 턴 60건이 3회 반복 프로토콜과 결합하면 비용이 크다 — 다중 턴만 1회 측정으로 낮출지.
