## 운영 함정 (측정·배포에서 반복 확인된 것)

- **재색인은 worker 프로세스의 코드 버전을 따른다.** 청커를 고치고 재색인을 걸었는데 청크가
  그대로였다(191개·평균 1,211·clause 0). 원인은 arq worker가 구 코드로 기동된 상태였던 것 —
  Python은 핫리로드가 없고, 잡은 정상 처리돼 `indexed`로 끝나므로 **조용히 실패한다.**
  코드 변경 후 재색인 순서는 ①worker 재기동 ②재색인 enqueue다. 컨테이너 배포는 이미지 교체로
  재기동되니 문제되지 않지만, 로컬·핫픽스 상황에서는 반드시 확인할 것.
- **api `--reload`는 `packages/*`를 감시하지 않는다.** cwd=`apps/api` 기준이라 `ai-core`·`db`
  수정이 반영 안 된 채 측정 2회가 무효가 됐다(R22). `--reload-dir`로 명시 수정(`apps/api/package.json`).
  단 이 플래그의 상대경로도 cwd=`apps/api` 전제 — api 기동은 반드시 `pnpm --filter @liviq/api dev`
  또는 `apps/api`에서 실행할 것(명령을 다른 위치에 복사 실행하면 같은 함정 재발).
  공통 패턴: **두 함정 모두 "조용한 구버전"** — 프로세스는 정상 동작하고 잡·응답도 성공하므로
  결과 숫자가 그럴듯하게 나온다. 코드 수정 후 측정 전, 로드된 코드(설명문·청크 수 등)를 출력해
  확인하는 절차를 표준으로 한다.

## R25 — 모델 티어 대조: 8B vs 14B (같은 40건 GraphRAG 비교)

**목적**: R24에서 "병목은 8B 도구 라우팅"이라 봤다 → 상위 모델이 그 상한을 뚫는지 검증(A안). vLLM(RTX 4080 SUPER 16GB)에서 8B 내리고 **Qwen2.5-14B-Instruct-AWQ**(tool-parser=hermes, gpu-util 0.92, offline 캐시) 기동 → `ai_backend_config.model` 재지정(endpoint 동일) → 같은 caseset·auth. 측정 후 8B 파일럿 복구. 결과 JSON: `rag500-2026-07-30T16-30-41-qwen25-14b.json`.

| 백엔드 | 8B(R24) pass·인용 | 14B(R25) pass·인용 |
|---|---|---|
| pgvector(문서) | 9/10 · 90% | **0/10 · 0%** |
| neo4j(그래프·추적) | 15/27 · 81% | **22/27 · 96%** |
| 전체 | 26/40 · 84% | 25/40 · 70% |
| p50 지연 | ~2000ms | ~3500ms |

hard_fail 0(양 모델). 14B가 8B보다 느림(파라미터 2배 예상 범위).

**핵심 발견 1 — 도구 라우팅 기본값이 모델 티어로 뒤집힌다.** pgvector 0%는 검색 실패가 아니다 — 14B가 **문서-라벨 병렬 케이스 9/10을 `search_facility_graph`로 라우팅**(tool_path 확인). 8B는 같은 질문을 `search_documents`로 기본 처리했다. 즉 8B=문서 기본, 14B=그래프 기본. neo4j 인용 81→96%·pass 15→22는 **14B의 그래프·trace 도구 인식이 확연히 강함**을 뜻한다 → A안 가설 확정: 8B의 그래프 도구 under-selection은 **모델 능력 상한이며 상위 모델이 뚫는다**.

**핵심 발견 2 — 병렬 쌍 인용 지표는 백엔드 검색 품질이 아니라 모델의 도구 선호를 잰다(방법론 한계).** 병렬 20건은 같은 설비-장애 질문을 문서/그래프 두 라벨로 물었는데, 모델은 라벨을 모르고 도구를 고른다. 8B는 문서를, 14B는 그래프를 선호 → 각 모델이 만족하는 라벨이 갈린다. **백엔드 검색 품질을 공정 비교하려면 도구를 강제하거나(forced-tool) 도구 선택과 무관하게 답변 정확도를 판정**해야 한다. 현 지표는 "어느 백엔드로 라우팅되나"를 재는 것(그 자체로 유의미 — 8B는 그래프 자산을 못 살리고 14B는 살린다). 보고서에 이 구분 명시.

**결론**: GraphRAG 인프라는 양 모델에서 동작·격리 유지(hard_fail 0). Neo4j 그래프/인과 자산의 실효 가치는 **모델 티어에 강하게 의존** — 8B는 그래프 도구를 과소 선택해 자산을 놀리고, 14B는 적극 선택해 그래프 클래스 품질이 급등한다. 파일럿이 8B면 그래프 투자 회수율이 낮다는 실측 근거. 다음: 병렬 쌍을 forced-tool로 재설계하면 백엔드 순수 검색 품질(라우팅 변인 제거)을 분리 측정 가능.

**교훈(방법)**: 프롬프트 한 줄 변경의 효과는 8B 변동폭(인용 ±2.5pp·pass ±3)보다 작을 수 있다. 단발·2회 측정으로 "좋아졌다/나빠졌다"를 말하지 말 것.

## R30 — H18 에이전트 심화 후 dev 회귀 (8B, ×3회) · **인용률 회귀 확인**

**환경**: dev api `c91bdce3`, llama3.1-8B-AWQ vLLM, 캐시 off. 케이스 89건(기존 82 + 멀티턴 3·되묻기 2·오남용 대조군 2). 도구 11종(`ask_clarification` 추가).

**동일 케이스(82건)로 맞춘 비교** — 신규 7건은 난이도가 달라 평균을 흔든다:

| 지표 | R29(H17) 3회 | R30(H18) 3회 | 판정 |
|---|---|---|---|
| pass | 75.6·79.3·76.8% | 76.8·68.3·74.4% | 범위 겹침(하락 의심) |
| 문서 [n] 인용 | 86.1·88.6·87.3% | 82.3·79.7·86.1% | **중위 87.3 → 82.3, 실질 하락** |
| 복합 완전호출 | 90.8·92.3·92.3% | 90.8·83.1·90.8% | r2만 이상치, 나머지 동일 |
| 되묻기 오남용 | — | 2.3·3.4·5.7% | **기준(10% 미만) 충족** |
| hardfail | 0 | 0 | 유지 |

**① 되묻기는 성공적이다.** 오남용 2.3~5.7%로 기준 이내고 hardfail 0. 도구 11종으로 늘렸는데 복합 완전호출률은 유지됐다 — `ask_clarification`이 다른 도구를 잡아먹지 않았다.

**② 인용률이 5pp 내려갔다 — H18-4 완료 기준 미충족.** 가장 유력한 원인은 `ANSWER_SYSTEM_PROMPT` 규칙 4 변경이다. 분량 지시("2~4문장")를 형식 지시("항목이 여럿이면 `- `로 나열")로 바꿨는데, **모델이 목록을 쓰기 시작하면 항목 끝에 `[n]`을 붙이지 않는다.** H15-2 R21(짧게 쓰라는 압력이 근거 문장을 지움)과 같은 계열 — **형식 압력이 인용 규율을 깎는다**는 패턴이 세 번째로 재현됐다.
   - 계획 turn·히스토리는 용의선상에서 낮다: 단일턴 케이스에는 히스토리가 없고, 계획 turn은 도구 결정 turn에만 관여하며 최종 답변 turn의 프롬프트를 바꾸지 않는다.

**③ 신규 대화 카테고리는 7건 중 1~2건 pass.** 멀티턴 3건은 2턴이 지시대명사에 의존하고, 되묻기 2건은 모델이 clarify를 고르는지 자체가 관건이다. 표본이 작아 이 숫자로 멀티턴 품질을 판정하지 말 것.

**다음 수단(미실행)**: 규칙 4에 "목록 항목에도 근거가 있으면 `[번호]`를 붙이십시오"를 명시하고 재측정. 그래도 안 오르면 형식 지시를 걷고 인용 우선으로 되돌린다 — **인용은 규칙 1의 하한이고 형식은 그 위의 편의다.**

### R30b — "목록 항목도 인용" 명시의 효과 = **없음(가설 기각)**

R30 §②의 가설(목록을 쓰면서 항목에 `[n]`을 안 붙인다)에 따라 규칙 2에 "목록 항목도 같습니다"를 추가하고 dev 재배포 후 2회 측정.

| 조건 | 인용(82건 동일 비교) | 중위 | 범위 |
|---|---|---|---|
| R29 H17 (3회) | 86.1 · 88.6 · 87.3% | 87.3 | 2.5pp |
| R30 H18 (3회) | 82.3 · 79.7 · 86.1% | 82.3 | 6.4pp |
| R30b H18+명시 (2회) | 79.7 · 86.1% | — | 6.4pp |

**기각.** 명시 전후가 구분되지 않는다. 목록 인용 누락은 원인이 아니었다.

**더 정확한 관찰은 "중위 하락"이 아니라 "변동폭 증가"다.** H17은 2.5pp 폭 안에 3회가 모였는데, H18 이후 5회는 79.7~86.1%로 6.4pp에 흩어졌고 그중 2회는 H17 범위와 겹친다. 계획 turn이 도구 결정 경로를 다양화하면서 최종 근거 구성이 회차마다 달라진 것으로 보인다 — 평균이 내려간 게 아니라 **분산이 커졌다**.

**판단**: 형식 지시를 롤백하지 않는다. 구조화 응답·목록은 사용자가 요구한 UX의 근간이고, 롤백해도 인용이 87%대로 복귀한다는 근거가 없다(변동폭 안). 인용 규율의 진짜 상한 돌파는 여전히 **상위 모델**의 몫이다(H15-2 본류 잔여, OpenAI 축 — 키 대기). 회차 간 분산이 커진 만큼 **앞으로 인용률 비교는 3회 이상 중위로만 하고 단발 비교를 금지한다.**
