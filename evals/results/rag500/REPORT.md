## 1. 무엇을 측정했나

LIVIQ는 아파트 관리 업무에 AI 응대를 얹는 시스템입니다. 입주민이 "층간소음 규정이 어떻게
되나요?"라고 물으면, AI가 **관리규약 같은 실제 문서를 찾아 근거와 함께** 답합니다. 지어내지
않고, 근거를 못 찾으면 담당자에게 연결합니다.

이 방식이 실제로 얼마나 정확하고 빠른지 재봤습니다.

**측정 대상**: 아파트 3개 단지분의 시험 데이터(문서 40건·세대 15개·관리비 72건)로 만든
**질문 500개**. 이 중 중요도 높은 **180개**를 반복 측정에 썼습니다.

**측정 항목 4가지**

| 항목 | 뜻 | 왜 중요한가 |
|---|---|---|
| 근거 적중률 | 답변에 붙은 출처가 정답 문서인지 | 엉뚱한 문서를 근거로 대면 신뢰할 수 없다 |
| 회피 정확도 | 모를 때 담당자 연결, 알 때 답변 — 양쪽 다 맞는지 | 아는데 회피하면 쓸모없고, 모르는데 답하면 위험하다 |
| 금지선 위반 | 지어내기·다른 단지 정보·개인정보 노출 등 | **한 건도 허용 안 됨** |
| 응답 속도 | 답이 나오기까지 걸린 시간 | 느리면 아무리 정확해도 안 쓴다 |

## 2. 결론 먼저

### 결론 1. AI를 돌리는 방식만 바꿔 속도가 7.7배 빨라졌습니다

같은 크기의 AI 모델을 노트북에서 돌릴 때와 GPU 서버에서 전용 엔진으로 돌릴 때를 비교했습니다.

| | 노트북 | GPU 서버 |
|---|---|---|
| 답변 완료까지 (보통) | 17.3초 | **2.3초** |
| 답변 완료까지 (느린 편) | 60.5초 | **9.2초** |
| 근거 적중률 | 50% | **70%** |

노트북에서 17초는 실사용이 불가능한 수준입니다. 2.3초는 쓸 수 있습니다.
**같은 AI라도 어디서 어떻게 돌리는지가 사용 가능 여부를 갈랐습니다.**

### 결론 2. 성능을 올릴 방법 8가지를 시험했고, 2가지만 효과가 있었습니다

| 시도한 방법 | 결과 |
|---|---|
| 문서를 더 많이 찾아오게 하기 | ✅ **효과 있음** — 채택 |
| 문서를 잘라 저장하는 방식 고치기 | ✅ **효과 있음** — 채택 |
| AI에게 근거를 더 많이 보여주기 | ✗ 변화 없고 느려짐 |
| 검색 기준을 느슨하게/엄격하게 조정 | ✗ 불필요 (이미 잘 찾고 있었음) |
| 검색 결과 재정렬 기능 추가 | ✗ 불필요 (이미 1등으로 찾아옴) |
| 검색 방식 이중화 | ✗ 기대 효과 없음 |
| AI에게 지시를 더 강하게 하기 | ✗ 변화 없음 |
| 실수했을 때 다시 요청하기 | ✗ 한쪽이 좋아지고 한쪽이 나빠짐 |

### 결론 3. 진짜 문제는 "못 찾는 것"이 아니라 "찾아놓고 출처를 안 적는 것"입니다

이게 이번 측정의 핵심 발견입니다.

AI는 **정답 문서를 정확히 찾아옵니다.** 그런데 답변에 **출처 번호를 안 적습니다.** 시스템은
출처 없는 답변을 신뢰할 수 없어 버리고, 입주민에게는 "담당자에게 연결해 드릴게요"가 갑니다.

실제 사례입니다:

```
질문: 층간소음으로 야간에 금지되는 행위는 무엇인가요?

AI가 쓴 답변: "① 입주자등은 오후 10시부터 다음날 오전 6시까지 다음 각 호의 행위를
              금지한다. 1. 뛰거나 문, 창문 등을 크게 소리나게 닫는 행위
              2. 망치질 등 세대내부 수리…"

→ 완벽히 맞는 답변입니다(관리규약 제60조 내용 그대로).
→ 그런데 "[3]" 같은 출처 번호를 안 붙였습니다.
→ 시스템이 폐기 → 입주민은 "담당자에게 연결해 드릴게요"를 받습니다.
```

**전체 질문의 17~21%가 이렇게 버려집니다.** 정답을 만들어놓고 못 전달하는 것입니다.

### 결론 4. 이 문제는 AI 모델을 바꿔야 해결됩니다

두 가지 처방을 시험했습니다. **둘 다 실패했습니다.**

- AI에게 "반드시 출처를 붙여라"고 더 강하게 지시 → 변화 없음
- 출처를 빠뜨렸을 때 "다시 붙여서 써달라"고 재요청 → 버려지는 답은 줄었지만 **엉뚱한 출처를 붙이기 시작**

지금 쓰는 AI는 **80억 개 규모(8B)의 작은 모델**입니다. 작은 모델은 지시를 끝까지 지키는 힘이
약합니다. 출처를 처음에 안 붙인 것도, 나중에 붙이라고 해도 제대로 못 붙이는 것도 **같은
한계**입니다. 소프트웨어를 고쳐서 넘을 수 있는 벽이 아닙니다.

→ **더 큰 모델(예: OpenAI)이 이 규율을 지키는지가 다음 검증 과제입니다.**

## 3. 진행 과정 — 무엇을 바꿨고, 결과가 어땠나

시간순으로 정리했습니다. 각 단계는 **변경 → 측정 → 판단**입니다.

### 1단계. AI 모델 8종 중에서 쓸 만한 것 고르기

AI가 문서를 검색하려면 스스로 "지금은 문서를 찾아봐야겠다"고 판단해 검색 기능을 호출해야
합니다. 이걸 못 하는 모델은 후보가 될 수 없습니다.

| 모델 | 결과 |
|---|---|
| **llama3.1 (80억)** | ✅ 검색 판단 안정 · 출처 규율 양호 · 3회 측정 모두 통과 → **채택** |
| Qwen3 (80억) | 자격은 통과. 그런데 **4.8배 느림**(2.9초 → 14.0초). 대신 악의적 질문 방어는 유일하게 완벽 |
| xLAM (80억, 검색 특화) | **검색 판단 10/10로 후보 중 최고.** 그런데 한 번에 검색을 4개씩 동시 호출해 비용 통제선을 넘고, 출처 규율도 약해 **탈락** |
| EXAONE 3.5 (78억, 한국어 특화) | 검색 기능을 붙일 자리 자체가 모델에 없음 → **자격 미달** |
| 그 외 4종 | 검색 미호출 / 외국어 섞임 / 응답 불능 → 탈락 |

**여기서 배운 것**: 벤치마크 순위가 우리 요구를 대변하지 않습니다. 검색 특화 모델(xLAM)이
검색을 가장 잘 호출했는데도 탈락했습니다. 우리에게 필요한 건 "많이 호출하는 능력"이 아니라
**절제된 호출 + 출처를 정확히 적는 규율**이었습니다.

**측정을 신뢰하기 위해 세운 원칙**: 처음에 Qwen3를 "부적격"으로 판정했는데 **재검증에서
뒤집혔습니다.** 원인은 모델이 아니라 설정이었습니다(엔진 옵션 하나, 메모리 여유). 그래서
"부적격 판정"에는 조건을 붙였습니다 — ①설정 조합 2가지 이상 시험 ②메모리를 단독 점유한
상태에서 측정 ③10회 이상 반복. 하나라도 빠지면 "모델 한계"와 "설정 실수"를 구분할 수 없습니다.

### 2단계. 문서를 몇 개 찾아올지 조정

AI가 질문을 받으면 관련 문서 조각을 몇 개 가져올지 정해야 합니다. 적으면 정답을 놓치고,
많으면 느려지고 비용이 늡니다. 4개·8개·16개를 각각 **3회씩** 재봤습니다.

| 가져올 개수 | 180문항 중 통과 | 관리규약 질문 근거 적중 |
|---|---|---|
| 8개 | 91~96 | 53% |
| **16개** | **97~107** | **80%** |

관리규약처럼 긴 문서는 조각이 많아(191개) 8개만 가져오면 관련 조항이 잘립니다.
**16개로 채택.** 대가는 응답 속도(느린 편 9.6초 → 14.5초)와 비용 증가입니다.

### 3단계. AI에게 근거를 더 많이 보여주기 → 기각

찾아온 16개를 AI에게 다 보여주는 게 아니라, 분량 제한이 있습니다. 이 제한을 2,400에서
4,000으로 늘려봤습니다.

| | 기존(2,400) | 늘림(4,000) | 판정 |
|---|---|---|---|
| 통과 문항 | 97~107 | 100 | 변화 없음 |
| 근거 적중률 | 54~60% | 58.6% | 변화 없음 |
| 응답 속도(느린 편) | 12.7~14.7초 | **17.3초** | **17% 느려짐** |

**품질은 그대로, 속도만 나빠졌습니다. 기각하고 되돌렸습니다.**

> 이 판단은 나중에 **부분 정정**됩니다. 5단계에서 문서 저장 방식에 결함이 발견되면서, 이
> 측정이 다른 문제에 가려져 있었다는 게 드러났습니다. 아래에서 설명합니다.

### 4단계. 채점 기준 자체가 틀렸다는 발견 ⚠️

"관리비 질문의 근거 적중률이 21%"라는 이상한 숫자를 파봤습니다. **AI 문제가 아니었습니다.**

시험 문제의 **정답표가 잘못 만들어져 있었습니다.** 시험 문제 500개는 AI로 생성했는데,
질문과 정답 문서가 어긋난 게 있었습니다. 문서 본문을 직접 읽어가며 검사해 **27건**을 찾았습니다.

| 어긋난 유형 | 건수 | 확인한 내용 |
|---|---|---|
| 공용전기·난방비를 묻는데 정답이 "관리비 설명 원칙" 문서 | 10 | 그 문서에 공용전기·난방비 얘기가 **한 줄도 없음** |
| 주차 차단기를 묻는데 정답이 "관리규약" | 8 | 규약에는 공사시간·반려동물만 있고, 답은 **회의록**에 있었음 |
| 급수펌프·소방을 묻는데 정답에 **엘리베이터 문서**가 섞임 | 9 | 엘리베이터 문서를 인용해야 점수를 주는 구조 — **틀린 답을 정답으로 만들고 있었음** |

세 번째가 가장 심각합니다. 급수펌프 질문에 엘리베이터 문서를 근거로 대면 점수를 받는
구조였습니다.

**정답표를 고칠 때 지킨 원칙 2가지**

1. **판단 근거는 문서 본문.** AI가 무엇을 인용했는지는 보지 않았습니다. AI 출력을 기준으로
   정답표를 고치면 "AI가 인용한 것이 정답"이 되어 순환 논리가 됩니다.
2. **점수를 올리려고 고친 게 아님.** 정답표가 맞는 25건은 손대지 않았고, 그 25건은 여전히
   실패로 남아 있습니다.

**교정 효과** (같은 데이터를 다시 채점 — 운에 좌우되지 않는 확정 수치)

| | 교정 전 | 교정 후 |
|---|---|---|
| 근거 적중률 | 58.6% | **71.6%** |
| 관리비 질문 | 21% | **79%** |
| 문서 개정판 구분 | 11% | **100%** |
| 여러 문서 종합 | 6% | **44%** |
| **나머지 6개 분야** | — | **변화 없음** |

마지막 줄이 중요합니다. 나머지 분야가 그대로라는 건 **교정이 정확히 결함 부분만 건드렸다**는
증거입니다(무차별로 점수를 올린 게 아님).

**여기서 배운 것**: 낮은 점수를 "AI 한계"로 결론짓기 전에 **시험 문제부터 검증해야 합니다.**
안 하면 존재하지 않는 문제를 고치느라 시간을 씁니다. 실제로 이 보고서 초안에는 "문서 개정판
구분은 시스템 기능상 불가능하다"고 적혀 있었는데, **틀린 진단이었습니다.**

### 5단계. 실제 문서를 저장하는 방식에 큰 결함 발견 ⚠️

실제 아파트 관리규약 PDF(10만 자)를 시스템에 넣어보니, 문서를 잘라 저장한 조각이
**정해진 크기의 3배**였습니다.

**무슨 일이 있었나** — 긴 문서는 검색을 위해 조각으로 잘라 저장합니다. 조각마다 "제48조
(주택관리업자 선정방법)" 같은 제목을 붙입니다.

문제는 PDF에서 글자를 뽑아내면 **줄바꿈이 사라진다**는 점입니다. 한 줄이 수천 자가 됩니다.
시스템은 "줄 끝까지가 제목"이라고 판단해, **제목 하나가 900단위**가 되었습니다. 그리고 그
거대한 제목이 **모든 조각에 복사**됐습니다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 조각 개수 | 191 | 286 |
| 조각 평균 크기 | 1,211 | **242** (기준: 400 이하) |
| 기준 초과 조각 | 186개 / 191개 | 24개 / 286개 |
| 조항 번호가 붙은 조각 | 0 | **284** |

**이 발견이 3단계의 판단을 정정합니다.** 조각 하나가 1,211이면 분량 제한 2,400에는
**2개**만 들어갑니다. 16개를 찾아와도 AI는 2개만 본 것입니다. 4,000으로 늘려도 3~4개뿐입니다.
즉 3단계에서 "근거를 더 줘도 AI가 못 쓴다"고 해석한 것은 **조각 크기라는 다른 원인이 섞인
결과**였습니다.

**조항 번호에서 더 심각한 문제도 나왔습니다.** 조항 경계를 "줄 시작"에서만 찾았는데, PDF에는
조 사이에 줄바꿈이 없어서 **우연히 줄 시작에 걸린 조항 하나가 뒤따르는 수십 개 조각의 제목을
가로챘습니다.** 제1조 내용이 **제64조로 인용**됐습니다.

> **틀린 조항을 가리키는 인용은 인용이 없는 것보다 나쁩니다.** 사용자가 확인하러 갔다가
> 엉뚱한 조항을 보게 됩니다.

수정 후 284개 조각 전부에서 조항 번호가 본문과 일치하는지 검사해 **284/284 일치**를 확인했습니다.

**실제 동작 확인** — 관리규약 조항을 묻는 질문 25개로 확인했습니다.

| | 결과 |
|---|---|
| 조항 번호가 출력된 질문 | 14~17건 |
| 정답 조항과 일치 | **14건** |

수정 전이라면 **전부 "제64조"**로 나왔을 것들입니다. 실제 출력 예시:
`제17조(동별 대표자의 선출)`, `제21조(보궐선거)`, `제71조(장기수선충당금의 세대별 부담액 산정방법)`.

### 6단계. 기준선 확정 — 이후 모든 비교의 잣대

같은 AI라도 **같은 질문에 매번 조금씩 다르게 답합니다.** 그래서 한 번 재고 "좋아졌다"고
말할 수 없습니다. 동일 조건 **3회 반복**으로 흔들리는 범위를 먼저 확정했습니다.

| 항목 | 범위 (3회) |
|---|---|
| 180문항 중 통과 | **116~125** |
| 근거 적중률 | **69.2~74.0%** |
| 회피 정확도 | 69.4~73.3% |
| **금지선 위반** | **0건 / 0건 / 0건** |
| 응답 속도(보통) | 3.2~3.4초 |

**이후 모든 판정은 "이 범위를 벗어났는가"로 했습니다.** 범위 안이면 개선이 아니라 운입니다.

### 7단계. AI에게 지시를 강하게 → 기각

"출처를 반드시 붙여라"는 지시는 **이미 있었습니다.** 그래서 관찰된 실패 양상에 맞춰 4가지를
보강했습니다: 길게 베끼지 말고 요약하라 · 문서 안의 번호(①, 1.)는 출처 번호가 아니다 ·
출처 없는 답변은 폐기된다는 사실 고지 · 이 지시를 첫 번째 규칙으로 이동.

| | 기준선 | 지시 강화 후 |
|---|---|---|
| 통과 문항 | 116~125 | 124 (범위 내) |
| 근거 적중률 | 69.2~74.0% | **68.6%** (범위 아래) |

**변화 없음. 기각하고 되돌렸습니다.**

의미 있는 정보이기도 합니다 — 지시를 어떻게 다듬어도 준수율이 오르지 않았다는 건
**작은 모델의 능력 한계**라는 진단을 뒷받침합니다.

> **측정 과정에서 자체 교정한 실수**: 지시문에 예시를 넣을 때 처음엔 "야간에는 세대 내부
> 수리를 금지합니다"라고 썼습니다. **그런데 이건 시험 문제 중 하나였습니다.** 정답을 미리
> 알려주고 채점하는 셈입니다. 바꾼 예시("방문 차량 등록")도 시험 문제 5개와 겹쳤습니다.
> 결국 **주제가 없는 형식 예시**로 확정했습니다. 문법만 가르치고 내용은 알려주지 않습니다.

### 8단계. 출처를 빠뜨리면 다시 요청 → 기각 (지표 상충)

AI가 출처를 안 붙였을 때, 버리기 전에 **한 번만 "같은 내용에 출처 번호를 붙여 다시 써달라"**고
요청하도록 만들었습니다. 없는 근거를 만들라는 게 아니라 **이미 쓴 답에 출처만 달라**는 요청입니다.

| 항목 | 기준선 | 재요청 (3회) | 판정 |
|---|---|---|---|
| **버려진 답변** | 35건 | **23 / 23 / 24** | ✅ 개선 |
| **회피 정확도** | 70.6% | **76.1 / 76.7 / 75.6%** | ✅ 개선 |
| **근거 적중률** | 122건 | **110 / 112 / 108** | ❌ **악화** |
| 통과·비용·속도 | — | 변화 없음 | — |

문항별로 보면 **19건이 나빠지고 5건이 좋아졌습니다.** 원인을 찾았습니다 — 나빠진 19건의
답변 길이가 **528자에서 413자로 22% 짧아졌습니다.**

재요청할 때 "근거가 없는 문장은 지워라"라고 지시했는데(지어내기를 막기 위한 안전장치),
AI가 **과하게 지워서 근거가 있는 문장까지 날렸습니다.** 그 과정에서 정답 출처를 잃었습니다.

**최종 판단: 되돌렸습니다.**

근거는 이렇습니다. **출처의 정확성은 이 시스템의 절대 규칙입니다.** 버려지는 답변 12건을
살리는 대신 정확한 출처 12건을 잃는 거래인데, **틀린 출처를 붙인 답변은 담당자 연결보다
나쁩니다.** 사용자가 확인하러 갔다가 엉뚱한 문서를 보게 되고, 그게 반복되면 시스템 전체를
못 믿게 됩니다.

> **측정 중 폐기한 가설**: 처음엔 "기준선은 AI가 출처를 남발해서 정답이 우연히 포함된 것"으로
> 봤습니다(실제로 한 답변에 문서 16개를 인용한 사례가 있었습니다). 그런데 전체를 세어보니
> **재요청 쪽이 더 남발**했습니다(답변당 2.79개 vs 2.43개). 가설 폐기.

품질 측정의 부수 효과가 측정 결과보다 컸습니다.

| 결함 | 영향 | 발견 경로 |

감사 기록은 보안 기록이고, 테스트 편의로 훼손하면 안 됩니다. 계정을 지우지 않고 갱신하는
방식으로 바꿨습니다.

않았다면 발견되지 않았을 것**입니다.

## 5. 최종 결정과 근거

### 결정 1. 파일럿 구성을 확정합니다

**llama3.1 (80억) · GPU 서버 전용 엔진 · 문서 16개 검색 · 근거 분량 2,400**

| 근거 | 실측 |
|---|---|
| 후보 8종 중 유일하게 검색 판단·출처 규율·속도를 모두 통과 | 3회 측정 100% |
| 2순위(Qwen3)보다 품질 우위 | 통과 59% vs 42%, 근거 적중 57% vs 47% |
| 2순위보다 4.8배 빠름 | 2.9초 vs 14.0초 |
| 검색 개수 16은 8보다 확실히 우위(운 아님) | 통과 범위 비겹침 97~107 vs 91~96 |
| 근거 분량 확대는 효과 없음 | 품질 변화 없고 17% 느려짐 |

### 결정 2. 검색 성능 개선은 여기서 멈춥니다

검색 결과 재정렬·검색 방식 이중화·문서를 숫자로 바꾸는 방식(임베딩) 교체 등
**검색을 더 좋게 만드는 방안은 진행하지 않습니다.**

근거는 하나입니다 — **검색은 이미 정답을 1등으로 찾아옵니다.**

| 버려진 답변의 질문 | 시스템이 1등으로 찾은 문서 | 유사도 |
|---|---|---|
| 층간소음 야간 금지행위 | 관리규약 제60조 (층간소음 생활규칙) | **0.717** |
| 전용·공용부분 범위 | 관리규약 제5조 (전용부분 및 공용부분의 범위) | 0.705 |
| 선거관리위원장 선출 | 관리규약 제39조 (위원위촉 및 구성) | 0.700 |

통과 기준이 0.35인데 실측이 0.70을 넘고, **순위도 1등**입니다. 순서를 다시 매기는 기능
(리랭커)을 넣어도 1등을 1등으로 만들 뿐입니다. **개선의 여지가 검색에 없습니다.**

### 결정 3. 남은 격차는 AI 모델 교체로만 해결합니다

**전체 질문의 17~21%가 정답을 만들고도 버려집니다.** 이 문제에 소프트웨어 처방 2가지를
시험해 둘 다 실패했습니다.

| 처방 | 결과 | 실패 원인 |
|---|---|---|
| 지시 강화 | 변화 없음 | 이미 "반드시 출처를 붙여라"였다. 무엇을 더해도 안 지킨다 |
| 출처 재요청 | 한쪽 개선·한쪽 악화 | AI가 사후에 출처를 붙이면 **틀린 출처**를 붙인다 |

두 실패가 같은 곳을 가리킵니다. **작은 모델은 출처 규율을 지키는 능력 자체가 부족합니다.**
처음에 안 붙인 것과 나중에 제대로 못 붙이는 것이 **같은 한계**입니다. 나중에 붙이라고
요구하는 처방은 부족한 그 능력을 다시 부르는 셈입니다.

> **명시적으로 배제한 방법**: 서버가 답변과 문서를 비교해 **출처를 대신 붙이는 방식**은
> 채택하지 않았습니다. 출처 없는 답변을 출처 있는 것처럼 만드는 것이고, 이 시스템의
> 절대 규칙(검증된 근거만 인용)을 무력화합니다.

### 결정 4. 다음 검증 과제

**더 큰 모델(OpenAI 등)이 출처 규율을 지키는지 확인합니다.** 목적이 명확합니다:

- **지킨다** → 작은 모델의 구조적 한계가 확인됩니다. 품질이 필요한 용도는 큰 모델,
  비용·보안이 우선인 용도는 작은 모델로 나누는 판단 근거가 됩니다.
- **지키지 않는다** → 모델 문제가 아니라 **우리 설계 문제**입니다. AI에게 주는 지시문과
  처리 흐름을 다시 봐야 합니다.

어느 쪽이든 결론이 나옵니다. 시험 문제 72건과 실행 절차는 준비돼 있고, **외부 API 키만
있으면 실행 가능**합니다.

## 6. 이 측정에서 배운 방법론

수치보다 재사용 가치가 큰 부분입니다.

**1. 한 번 재고 판단하지 말 것.** 같은 조건에서도 결과가 흔들립니다(분야별 최대 8%p).
3회 반복으로 범위를 먼저 만들고, 그 범위를 벗어나야 개선으로 인정했습니다. 이 규율이 없으면
운을 성능으로 착각합니다.

**2. 낮은 점수를 AI 탓으로 돌리기 전에 시험 문제를 검증할 것.** 정답표 결함 27건을 못 찾았다면
존재하지 않는 문제를 고치느라 시간을 썼을 겁니다. 실제로 이 보고서 초안에는 **틀린 진단
3개**가 있었고 전부 정정했습니다.

**3. "모델이 못한다"는 판정은 쉽게 오판된다.** Qwen3를 부적격으로 판정했다가 재검증에서
뒤집혔습니다. 원인은 모델이 아니라 설정이었습니다. 그래서 판정 조건을 성문화했습니다
(설정 2가지 이상 · 메모리 단독 점유 · 10회 이상 반복).

**4. 시험 문제의 내용을 AI 지시문에 넣지 말 것.** 정답을 알려주고 채점하는 것입니다.
두 번 실수하고 두 번 되돌렸습니다.

**5. 측정은 품질을 재는 동시에 결함을 드러낸다.** 이번에 7건을 찾았고, 그중 3건은 측정
없이는 발견되지 않았을 것입니다. 한 건은 앞선 측정의 해석까지 바꿨습니다.

## 부록. 운영 시 주의점

- **문서 재색인은 처리 프로그램의 코드 버전을 따릅니다.** 문서 처리 방식을 고치고 재색인을
  걸었는데 결과가 그대로였습니다. 처리 프로그램이 옛 코드로 떠 있었고, 작업은 정상 완료로
  기록되어 **조용히 실패**했습니다. 순서는 ①프로그램 재시작 ②재색인입니다.
- **AI 응답 캐시를 켠 상태로는 측정할 수 없습니다.** 첫 측정에서 "응답 15.6초인데 첫 글자는
  28밀리초"라는 모순이 나왔습니다. 캐시된 답을 재생한 것이었습니다.
- PDF에서 뽑은 글자는 줄바꿈·문장 사이 공백을 잃습니다(실측: 문장 경계 1,832곳에 공백 없음).
  문서 처리 로직은 이걸 전제해야 합니다.
