# 그래프 시드 설계 (G1 — 검토용) · 첫마을 4단지

> 상태: **리뷰 2회 반영(codex·cursor)** · 근거: [GRAPHRAG-COMPARISON-PLAN.md](../../GRAPHRAG-COMPARISON-PLAN.md)
> 원칙: `facilities.status` **불변**(현재 전부 normal 유지). 과거 이력만 추가.
> 전부 회의록에 실재하는 장애와 정합 → 문서(pgvector) vs 그래프(Neo4j) 교차 검증 가능.

> "보고" 문맥에서 발생 시점을 역산해 회의일보다 앞선 날짜로. 재실행 재현(난수 없음).

**인과 엣지 `CAUSED_BY` (다단계 원인 — 리뷰 HIGH 반영, 옵션 A 확정)**

두 리뷰가 공통 지적: 현재 그래프 관계는 `HAS_INCIDENT·HAS_MAINTENANCE·LINKED_TO`뿐 —
incident 간 인과 엣지가 없어 다단계 추적이 "같은 설비·시간순" 암묵 추론이 되고 GraphRAG
강점을 입증 못 한다. **실제 인과 엣지를 만든다:**

- 스키마: `incidents.caused_by_incident_id` self-FK(nullable, tenant 스코프) 추가(Alembic).
- 그래프: `merge_incident`에 `Incident-[:CAUSED_BY]->Incident` 엣지 배선 + 재색인 전달.
- 탐색: `expand_incidents`에 `CAUSED_BY` 다단계(2~3 hop) 경로 조회 추가.

인과 연쇄 4개(graph:chain 8건 근거):

## 3. 겹침 문서 1건 (병렬 표현 축) — 리뷰 반영

제목 `설비 장애·정비 이력 요약(2024~2026)`, category=지침/기록. incident 중 **10건**
(#1·2·4·5·6·8·9·10·12·13 — 계획의 병렬 10쌍 정합, cursor M4-3)을 서술형으로 기술.

**공정성 통제(정보량만으론 불충분 — 두 리뷰 M4 수렴):**
- 각 서술은 해당 incident의 symptom·root_cause·resolution과 **같은 사실·같은 정보량**.
- **청크 경계 고정**: 문서를 incident당 1청크가 되도록 분할(문서 1건→여러 청크의 top_k
  편향 제거). pair별 청크 수·토큰 수를 매니페스트에 기록.
- **질의 문구 대칭**: 같은 장애의 문서 질의와 그래프 질의를 **동일 문장**으로(pair_id로 묶음).
- **잔여 편향 명시**: 표현·정보량을 맞춰도 검색 **메커니즘 차이**(pgvector 임베딩 유사도 vs
  Neo4j 벡터인덱스+관계 expand)는 남는다 — 이건 제거 대상이 아니라 **비교의 대상 자체**.
  보고서에 "정보량 통제 후 남는 차이 = 백엔드 메커니즘 차이"로 명시(과소 선언 회피).
- 재색인으로 pgvector 청크 생성 → 같은 장애를 문서·그래프 양쪽으로 질의.

## 4. LINKED_TO 배선 (세대 기기 → 설비) — 리뷰 반영

**기존 엣지 재사용**(SERVED_BY 신규 아님 — 두 리뷰 HIGH): client.py:350·527이 이미
`device.facility_id`가 있으면 `PlanDevice-[:LINKED_TO]->Facility`를 만들고 조회한다.
`plan_devices.facility_id`를 채우면 재색인이 자동으로 `LINKED_TO` 반영 — 신규 관계 불필요.

`plan_devices.facility_id`를 device_type → 계통 **단일 facility**로 채움(FK는 단일이라
계통에 설비가 여럿이면 대표 1개 선택):

| 세대 기기(device_type) | 계통 | 대상 facility(단일) | 닿는 incident |
|---|---|---|---|
| 화재감지기·소화기 | FR | **FR-CMN-05 화재수신반**(대표) | #6 |
| 콘센트·분전함 | EC | EC-CMN-01 수전설비 | #13(EV는 EC-02) |
| 수도 차단밸브 | WT | WT-CMN-04 부스터펌프 | #4·14 |
| 난방 분배기·보일러·온도조절기 | HT | HT-CMN-01 열교환기 | #5 |
| 월패드·통신단자함·TV·인터넷 단자 | NW | NW-CMN-01 홈넷 서버 | #10·11 |

**FK 단일 제약(cursor 지적)**: 세대 소화기 민원은 소방펌프·스프링클러도 관련이나 FK는
하나 → 대표 설비(화재수신반)로 잇고, 도구가 런타임에 **같은 code 접두(FR-*) 전체**로
확장 조회. 즉 배선은 진입점 1개, 탐색은 계통 전체.

**승강기(리뷰 HIGH 4)**: 승강기는 세대 평면도 마커가 아니다(plan_devices에 없음) →
`facility_id` 배선 대상 아님. "우리 동 승강기" 질의는 도구가 **런타임 조인**
(household→building→`EL-<building>-*`)으로 처리. 동별 스코프는 여기서 성립.

**미매핑 device_type 구분(리뷰 지적)**: 가스밸브·에어컨 배관·경량칸막이·room은 대응
공용 설비 계통이 없다(SC·PK도 세대 기기 아님). 이들은 `facility_id=NULL` 유지 —
**"미모델링"**(계통 자체가 그래프에 없음)이고, FR·WT 등 매핑된 계통에 이력이 없는 건
**"이력 없음"**(빈 결과 카드)과 구분. 채점에서 두 경우를 다르게 판정.

## 5. 규모·불변식

- incident **16**(14 + 선행 2 #4b·#6b) · maintenance 22 · 겹침 문서 1(10건 서술) ·
  `CAUSED_BY` 인과 엣지 4 · `LINKED_TO` 엣지(매핑된 계통 세대기기만)
- **불변**: `facilities.status`(전부 normal) · `facilities.next_check_at`(전부 NULL)
- **status 긴장(리뷰 L1)**: 미해소 건(#10·#11 홈넷)은 status=normal과 논리 긴장 —
  설비는 우회 작동 중이라 완전 모순은 아니나, resolution에 "미해소"를 명시해 봉합.
  완료 건(#1~#9·#12~#14)은 "과거 장애→조치 완료→현재 정상"으로 자연 정합.
- **결정론**: occurred_at은 실발생일 절대 시각, 난수 없음 → 재실행 재현.
- **테넌트**: 첫마을(`11111111-…`)만. RLS·tenant_id 명시.

## 6. 리뷰 반영 (codex + cursor · 2026-07-30)

**두 리뷰 공통 오탐(반영 안 함)**: facility code 재바인딩 권고 — 둘 다 시드 스크립트
순서로 code를 추론했으나 서버 자동 부여라 실 DB와 다르다. 실 DB 재조회로 SEED code 전건
정합 확인(FR-CMN-05=화재수신반·WT-CMN-04=부스터펌프·CM-CMN-01=어린이놀이터·EL-402-01=
402동 2호기). 정적 리뷰 2개가 같은 오답에 수렴 — DB를 센 쪽만 반증 가능.

**수용한 실결함 6건**: ①SERVED_BY→LINKED_TO(기존 재사용, §4) ②홈넷 미해소 정확 표기
(§1 #10·11) ③occurred_at=실발생일 정의(머리말) ④승강기 런타임 조인·배선은 공용 계통만
(§4) ⑤공정성=청크경계+질의대칭+10쌍+메커니즘 차이 명시(§3) ⑥미모델링 vs 이력없음 구분(§4).

**큰 결정(사용자 A 확정)**: 인과 엣지 `CAUSED_BY` 실제 추가(스키마 self-FK + 그래프
클라이언트 + 재색인 + 탐색). GraphRAG 다단계 강점을 실측 가능하게 — §1 인과 연쇄 4개.

## 7. 구현 범위(G1 — 리뷰로 확대)

1. **Alembic**: `incidents.caused_by_incident_id` self-FK(nullable, tenant 스코프).
2. **그래프 클라이언트**: `merge_incident`에 `CAUSED_BY` 엣지, `expand_incidents`에 2~3 hop
   경로 조회.
3. **재색인(ai-worker)**: incident sync에 `caused_by_incident_id` 전달.
4. **seed_graph.py**: incident 16·maintenance 22·겹침 문서 1·`plan_devices.facility_id`
   배선 → 재색인 enqueue. status·next_check_at 불변 assert.
5. **검증**: 시드 후 Neo4j에서 `CAUSED_BY`·`LINKED_TO` 엣지 수·2 hop 경로 존재 확인.
